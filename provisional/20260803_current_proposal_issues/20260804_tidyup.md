## Executive assessment

**Recommendation: do not advance the set to Release Candidate yet.**

The main blockers are behavioral rather than editorial:

1. Expression evaluation still has unresolved semantics. The proposal maps externally supplied expression values to animation time, but does not define the treatment of animation channels not selected by an expression extension or the mixing behavior when expressions overlap.
2. `KHR_node_visibility_hint` cannot implement its stated descendant-override behavior by setting `KHR_node_visibility` on an ancestor. The latter always hides the entire subtree.
3. Camera and visibility “roles” mix normative behavior with advisory hints, and the active view-context model is not defined.
4. Several schemas validate structurally invalid or semantically empty objects, and most cross-object rules are not fully specified.

The safest path is to advance independently useful extensions separately. In particular, the expression execution model, reference-pose model, and view-context model should not be frozen merely because they are in one PR.

## Cross-cutting specification issues

- **GEN-01 — Normative language is inconsistent (Major).** The visibility and camera documents declare RFC 2119, while the character documents use lowercase “must”, “should”, and “may” for requirements. Adopt RFC 2119/8174 consistently and distinguish normative text from recommendations.
- **GEN-02 — “Advisory” support conflicts with `extensionsRequired` (Blocker).** Several hint extensions say supporting runtimes MAY ignore the feature, while also recommending `extensionsRequired` when presentation depends on it. A runtime that claims support must have a testable minimum behavior; otherwise `extensionsRequired` gives no guarantee.
- **GEN-03 — Required-extension guidance is incomplete (Major).** The character and expression documents mandate `extensionsUsed` declarations but do not state when they belong in `extensionsRequired`, even when losing expressions or retargeting data may make the asset unusable for its intended purpose.
- **GEN-04 — The transitive `KHR_xmp_json_ld` dependency is unnecessary (Major).** Every character-family asset must advertise and every consumer must support XMP even when no metadata packet exists. Make XMP optional unless actual character metadata is present, or justify what required behavior an XMP-capable consumer provides when there is no packet.
- **GEN-06 — Multiple-scene semantics are missing (Major).** `rootNode`, camera targets, look-at targets, and world-space hints do not say which scene owns them, whether they must be reachable from the default scene, or what happens when the same document has several scenes.
- **GEN-07 — Visibility-extension scope needs an explicit note (Major).** In both visibility extension specifications, state that, since `KHR_character` assumes one character per glTF asset, these extensions do not define character ownership or per-character view-context selection.
- **GEN-12 — Cross-object containment is not defined (Major).** Referenced nodes and channels are checked only as document indices. The specifications must say whether they must belong to the character subtree, an applicable skin, or the same scene.
- **GEN-13 — Redundant index/name pairs add a failure mode (Major).** Mask, expression mapping, and skeleton mapping objects resolve by index but optionally repeat a name that MUST match. This adds edit fragility without changing identity. Remove the duplicate name, make it purely non-normative debug metadata, or give it a defined recovery purpose.
- **GEN-14 — Array-edit behavior is not stated (Minor).** Tools must update expression, animation, node, camera, and channel indices when arrays are reordered. Add a common authoring/round-trip requirement.
- **GEN-15 — Extension partitioning is not justified (Major).** The three expression target extensions contain only channel-index arrays whose target domain can usually be inferred from animation paths. Specify the capability-negotiation benefit and unsupported-domain fallback, or merge them into one expression-channel binding model.
- **GEN-16 — Partial implementation is not defined (Blocker).** A runtime may support morph expressions but not joint or texture expressions. The proposal does not define whether an expression is partially applied, rejected, or considered unsupported, nor how this interacts with `extensionsRequired`.
- **GEN-17 — Composition across extensions is not fully specified (Blocker).** Expressions, masks, mappings, visibility, camera hints, and look-at targets make cross-extension claims, but there is no normative evaluation pipeline or state diagram.
- **GEN-18 — KHR scope and maturity are mixed (Major).** General camera, visibility, and look-at metadata are bundled with the character family even though they are independently useful and have different implementation risks. Evaluate and advance them separately.
- **GEN-19 — Requirements are repeated and drift (Minor).** The same expression timing, interpolation, and blending prose is copied across several READMEs and already differs. Put shared normative behavior in `KHR_character_expression` and make subextensions reference it.
- **GEN-20 — No explicit error model exists (Major).** Define whether invalid references, duplicate mappings, unsupported custom types, and contradictory annotations make an asset invalid, make an extension instance ignored, or trigger a warning with fallback.

## `KHR_character`

- **CHAR-01 — `rootNode` has only a SHOULD-level meaning (Blocker).** The only required property may reference any node. If all character meshes, skins, mappings, and hints need not be under it, consumers cannot reliably determine character membership. Define mandatory containment or a precise alternative.
- **CHAR-02 — Scene reachability is unspecified (Major).** `rootNode` may be absent from every scene or present only in a non-default scene. Define validity and behavior for both cases.
- **CHAR-03 — Multiple-character scope needs an explicit statement (Major).** State that `KHR_character` describes at most one character in a glTF asset and that representation of multiple characters within a single asset is outside the scope of this extension.
- **CHAR-04 — The marker's conformance value is unclear (Major).** The document says the marker causes character-specific pipelines to be used, but gives no minimum behavior for a consumer that supports only `KHR_character`. Define what support means beyond reading `rootNode`.
- **CHAR-06 — The proposed Khronos JSON-LD namespace does not exist (Blocker).** The example uses `https://www.khronos.org/registry/glTF/character/metadata/`, while the text admits it is unpublished. Do not publish RC examples using terms without a resolvable, versioned context.
- **CHAR-07 — Dublin Core terms are mixed incorrectly (Major).** `dc:created` and `dc:license` are shown under the Dublin Core Elements 1.1 namespace, but those terms belong to DCMI Terms. Correct the context and define value shapes.
- **CHAR-08 — `khr:thumbnailImage` embeds a glTF index in generic metadata (Major).** Its reference semantics, allowed image types, index-update requirements, and validator rules are not defined by either schema. Prefer an ordinary typed extension property if it is a glTF object reference.
- **CHAR-09 — The example does not demonstrate character membership (Minor).** It has one empty root node and metadata, but no mesh, skin, expression, or descendant validation case. Provide a minimal complete character and a negative out-of-subtree case.

## `KHR_character_expression`: core execution model

- **EXP-01 — The expression driver API is undefined (Major).** Specify whether applications address expressions by array index, label, mapping-set target, or another handle; whether multiple entries with the same label are driven together; and how missing names are handled.
- **EXP-02 — Expression labels may be empty (Major).** The schema needs `minLength: 1` or a defined meaning for an empty label.
- **EXP-03 — Duplicate expression labels are deliberately possible but unresolved (Blocker).** Indices disambiguate internal references, but an application receiving a semantic command such as `blink` cannot know which duplicate to drive.
- **EXP-07 — Out-of-range input behavior is not an expression rule (Major).** Make `[0, 1]` a MUST for supplied and masked values, and say whether implementations clamp, reject, or preserve out-of-range values.
- **EXP-08 — The inactive pose is not guaranteed (Blocker).** At expression value `0`, glTF clamps to the first sampler output. Nothing requires that output to equal the node, morph, or material base value. Define and validate the inactive state.
- **EXP-09 — A single-keyframe animation cannot interpolate from rest (Major).** It produces the same output for every expression value. If implicit interpolation from the base value is intended, specify it; otherwise require at least two keys for continuous expressions.
- **EXP-10 — Channels not selected by an expression extension have no defined behavior (Major).** When an expression references an animation, the proposal does not specify what happens to channels absent from its typed `channels` list. Decide whether the specification should explicitly leave these channels undefined, or prescribe ignoring, ordinary animation behavior, or invalidation.
- **EXP-11 — Untyped expression entries have undefined output (Blocker).** The core examples contain entries with no joint, morph, or texture subextension. State whether all channels execute, none execute, or the asset is invalid.
- **EXP-12 — Channel overlap across subextensions is allowed (Major).** A channel can appear in more than one typed list. Require disjoint sets or define why duplicate classification is meaningful.
- **EXP-13 — Channel overlap across expressions is allowed (Blocker).** Different expressions may target the same property through different animations. The proposal explicitly leaves mixing runtime-defined, preventing reproducible rendering.
- **EXP-14 — Reusing one animation for several expressions is ambiguous (Blocker).** The mapping example assigns three expression entries to animation 0. Driving them to different values requires evaluating one animation at multiple times and then resolving overlapping outputs.
- **EXP-15 — Mixing semantics are a core requirement, not a known limitation (Blocker).** Define override/additive behavior, base values, ordering, normalization, quaternion handling, and conflict resolution, or constrain assets so overlapping targets are invalid.
- **EXP-16 — “Transforms scale proportionally” is not glTF sampling behavior (Major).** Animation outputs are sampled values; translations, scales, and quaternions are not multiplied by expression input. Replace this prose with an exact sampling and composition algorithm.
- **EXP-17 — Binary-expression guidance is underspecified (Major).** With `STEP`, the transition point comes from sampler input keys, not simply from values 0 and 1. Define authoring requirements and avoid treating inherently continuous controls such as `jawOpen` as necessarily binary.
- **EXP-18 — Facial scope is inconsistent (Minor).** The overview says facial expressions, while the category text permits down-chain meshes and broad gestures. Decide whether non-facial pose controls belong here and name the feature accordingly.
- **EXP-19 — Character containment is not validated (Major).** Selected channels can animate unrelated scene nodes and materials. Define whether that is legal and how a character-scoped expression is identified.
- **EXP-20 — The schema closes expression entries to future properties (Major).** The anonymous expression item uses `additionalProperties: false`, contrary to the repository convention that glTF property schemas allow additional properties. Factor it into a named schema inheriting `glTFProperty`.

## `KHR_character_expression_joint`

- **JNT-01 — “Joint” channels need not target joints (Blocker).** Any node TRS channel satisfies the prose. Require membership in an applicable `skin.joints`, or rename the extension to node-transform expressions.
- **JNT-02 — The applicable skin is unknown (Major).** A document may contain multiple skins and the same node may participate in none or several. Define how the character and selected joint channels associate with skins.
- **JNT-03 — `KHR_animation_pointer` handling is missing (Major).** Clarify whether pointers to `/nodes/{}/rotation`, translation, or scale are allowed, and align the rule with the morph-target extension.
- **JNT-04 — A core target without `node` must be rejected (Major).** The channel classification needs a semantic validation rule requiring an actual TRS target node.
- **JNT-05 — Quaternion mixing guidance is not sufficient (Blocker).** `exp(lerp(log(q0), log(q1), w))` does not by itself define sign selection, normalization, branch choice, or accumulation of multiple rotations. Use a rigorously specified operation and test vectors.
- **JNT-06 — Multi-expression joint composition is undefined (Blocker).** Eye-up plus eye-right, or smile plus blink on the same face joint, can produce different results depending on order and engine animation mixer behavior.
- **JNT-07 — Absolute versus additive transforms are unspecified (Blocker).** State whether sampled TRS replaces the base transform, blends from it, or composes as a delta. Translation, rotation, and scale need separate exact formulas.

## `KHR_character_expression_morphtarget`

## `KHR_character_expression_mask`

- **MASK-01 — The general composition equation is missing (Blocker).** Provide one normative formula for all masks affecting each target, including the per-mask factor and the final output.
- **MASK-02 — Input range is only a recommendation (Blocker).** Values outside `[0, 1]` can produce negative or amplified outputs. Make the domain and clamping/rejection rule normative.
- **MASK-03 — Unknown custom mask types have no runtime fallback (Blocker).** Preservation alone is insufficient. State whether an unsupported type is ignored, treated as `blend`, or makes the expression/asset unsupported.
- **MASK-04 — Custom type names can collide (Major).** Require a vendor/URI namespace and reserve standard names. Otherwise a future standard type can change the meaning of existing assets.

- **MASK-07 — Threshold boundary behavior needs tests (Major).** The formula uses `source > threshold`, not `>=`. Preserve that exact choice normatively and add tests at `threshold - epsilon`, `threshold`, and `threshold + epsilon`.

- **MASK-09 — Self-masking is valid but unspecified (Major).** An expression may target itself. Explicitly prohibit it or define the output from the raw input.
- **MASK-10 — Cyclic masks need an explicit rule (Major).** The order-independence claim relies on every mask reading pre-mask inputs. State that normatively and test mutual and longer cycles.

- **MASK-13 — `name` is redundant and rename-fragile (Minor).** Resolution always uses `target`; requiring a duplicated display name to match adds no behavior.

- **MASK-15 — “Mask” may be misleading terminology (Minor).** In graphics and animation, a mask often selects spatial components or channels; this extension applies directed expression-level attenuation. Consider `inhibition`, `override`, or clearly define the term.

- **NVIS-01 — Descendant override contradicts `KHR_node_visibility` (Blocker).** If a `third_person` parent becomes `visible: false` in first-person, `KHR_node_visibility` recursively hides every child, so a child annotated `always` cannot override it as promised.

- **NVIS-03 — Per-view evaluation cannot mutate one global visibility property (Blocker).** Simultaneous first-person and mirror/spectator renders require different results from the same nodes in the same frame.
- **NVIS-04 — Active view context is undefined (Blocker).** Specify the state, its scope, how applications set it, whether multiple contexts can be active, and whether it is tied to a particular camera hint.
- **NVIS-05 — `third_person` does not mean third-person-only (Major).** Its actual semantics are “visible in every context except first-person.” Rename it (for example, `not_first_person`) or make the asymmetry unmistakable.
- **NVIS-06 — `first_person` is asymmetric with custom contexts (Major).** It is hidden in portrait, mirror, detail, and unknown contexts, while `third_person` is visible in them. Confirm this is intentional with a complete truth table.
- **NVIS-07 — Custom roles have no visibility function (Major).** A custom string does not say whether it is inclusive, exclusive, or compatible with multiple contexts. A list of included/excluded contexts may be more extensible than one role token.
- **NVIS-08 — Camera-hint activation is asserted but not defined (Blocker).** The visibility README says activating a camera hint enters a context, but the camera extension does not normatively define such a state transition.
- **NVIS-10 — `always` override semantics need a normative example (Major).** This is the case that exposes the incompatibility with ancestor `KHR_node_visibility`; include it in tests.
- **NVIS-11 — Support requirements are too weak (Major).** A supporting implementation only SHOULD resolve and render roles correctly. For testable extension support, standard-role behavior must be MUST-level.
- **NVIS-12 — Required/fallback guidance is inconsistent (Major).** The document discourages `extensionsRequired`, even though rendering the inside of a head may be unacceptable. State exact author guidance and exact behavior for supporting runtimes.
- **NVIS-13 — Inheritance through non-visual nodes needs definition (Major).** Clarify whether inherited roles affect lights and other visual features consistently with `KHR_node_visibility`, while cameras and interactivity remain unaffected.

## `KHR_mesh_primitive_visibility_hint`

- **PVIS-01 — It inherits the undefined view-context model (Blocker).** Resolve the active context before freezing primitive roles.
- **PVIS-02 — `third_person` has the same misleading asymmetric meaning (Major).** Publish a full context truth table and settle the name.

- **PVIS-04 — Runtime requirements are SHOULD-level (Major).** An implementation that claims support can still ignore standard roles. Use MUST for the standard behavior.
- **PVIS-05 — Transparent-material substitution is not equivalent to culling (Major).** It may alter depth, shadows, picking, ray tracing, sorting, motion vectors, and performance, and alpha zero is ignored by `OPAQUE` materials. Do not RECOMMEND it as semantically equivalent without listing these constraints.
- **PVIS-06 — Mesh reuse is not discussed (Major).** A mesh primitive may be instanced by several nodes. Specify that primitive-role evaluation occurs per node instance and combines with that instance's context.
- **PVIS-08 — Required-extension capability needs a definition (Major).** A runtime that can hide nodes but cannot independently suppress a primitive must not claim support for this extension.
- **PVIS-09 — No tests cover non-color passes (Major).** Add expected results for shadows, depth prepass, picking, outlines, reflections, and ray queries, or explicitly limit the extension to camera color rendering.

## `KHR_node_camera_hint`

- **CAM-01 — The extension duplicates core camera-node composition (Major).** A node can already reference a camera with `node.camera`. Explain why a second `camera` property is necessary instead of annotating an ordinary camera node with role metadata.
- **CAM-02 — `camera` is confusingly named (Minor).** On a node that already has core `camera`, the extension property looks equivalent but has weaker advisory semantics. Rename it to `cameraReference`/`projection` or reuse core.
- **CAM-03 — Roles have two incompatible transform meanings (Blocker).** Most roles interpret the node position as camera position, while `orbit_center` and `framing_target` interpret it as a target point. Split these concepts or enforce role-specific schemas.
- **CAM-04 — Role/property combinations are unconstrained (Major).** `orbit_center` may contain a camera and `targetNode`; `framing_target` may contain projection data; none has defined meaning. Add conditional rules or prohibit meaningless combinations.
- **CAM-05 — “Full body” and “portrait” lack a subject (Blocker).** The runtime cannot know which hierarchy to frame, especially in multi-object scenes. Add a subject/root reference or narrow these roles to authored camera poses only.
- **CAM-06 — Framing is not reproducible (Major).** Aspect ratio, safe margins, viewport, bounding volume, and whether hidden geometry contributes are unspecified. Do not promise interoperability for framing roles without these inputs.
- **CAM-07 — `targetNode` does not define roll/up (Blocker).** A look direction alone leaves one rotational degree of freedom. Define how node rotation, local +Y, or world up determines roll.
- **CAM-08 — Coincident target positions are not handled (Major).** Self-reference is forbidden, but a different target node may occupy the same world-space point. Define fallback orientation.
- **CAM-09 — Same-scene/world-space validity is missing (Blocker).** A hint and target in different scenes have no shared instantiated world space. Require a common scene and define behavior for uninstantiated nodes.
- **CAM-10 — Animation timing is unspecified (Major).** Hint and target nodes may be animated. State whether hints are sampled at initial time, continuously followed, or evaluated by the application.
- **CAM-11 — Ignoring scale is incomplete (Major).** Parent scale still affects world position, and nonuniform/negative scale affects extracted orientation. Define transform decomposition and invalid cases.
- **CAM-12 — Multiple `default_view` selection is not deterministic (Major).** “First in node traversal order” has no canonical meaning across multiple scenes and traversal algorithms. Use explicit priority/default selection or a defined array order.
- **CAM-13 — Standard-role guarantees are only SHOULD-level (Major).** If runtimes may ignore all hints, the stated interoperability guarantee and use in `extensionsRequired` are not testable.
- **CAM-14 — Custom-role fallback may expose unintended UI (Minor).** Treating every unknown role as a selectable generic camera position can show internal markers. Define a safer discovery/UI rule.
- **CAM-15 — `label` overlaps core `node.name` (Minor).** Explain why both exist, how localization works, and which one tools should display.
- **CAM-16 — The viewer comparison table is unsourced and unstable (Minor).** Remove it or cite reproducible versions and tests; it is motivation, not normative evidence.
- **CAM-17 — Contributor metadata is unfinished (RC gate).** The README still contains “Additional contributors TBD.”

## `KHR_node_lookat_target`

- **LOOK-01 — There is no consumer-to-target link (Blocker).** Discovery of all marked nodes does not tell an eye, head, camera, sign, turret, or constraint which target to use.
- **LOOK-02 — `hint` is optional and free-form (Blocker).** An empty extension object carries only “something may look here,” which is insufficient for deterministic interoperability.
- **LOOK-04 — One node cannot express several hints (Major).** The text says a node may serve as `eye_target`, `head_target`, and `gaze_target` simultaneously, but the schema has one scalar `hint` string.
- **LOOK-05 — Multiple matching targets have no selection or priority (Blocker).** This is acknowledged as a known limitation but prevents deterministic behavior for common scenes.
- **LOOK-06 — Target ownership and scene scope are missing (Blocker).** Generic discovery can select a target belonging to another scene or application subsystem.
- **LOOK-07 — Examples infer behavior not encoded by the extension (Major).** `tour_stop` does not define sequence; wayfinding targets do not link signs to destinations; feature callouts have no labels/content; network replication is outside static glTF data.
- **LOOK-08 — VRM integration is not formal (Major).** The known limitations admit there is no link from VRM look-at to the target. Do not describe automatic composition as if it were portable behavior.
- **LOOK-09 — The expression integration diagram overclaims (Major).** The current expression extensions do not define the procedural gaze-angle/range-map pipeline shown in the diagram.
- **LOOK-10 — `lookat` naming should be settled (Minor).** Confirm whether glTF naming should use `look_at` to follow lowercase snake-case tokenization.
- **LOOK-11 — Required-extension guidance is too absolute (Major).** If application behavior depends on discovering targets, normal glTF mechanics allow `extensionsRequired`; the document's blanket SHOULD NOT needs justification.
- **LOOK-12 — The empty-object KHR extension needs a stronger value proposition (Major).** If no standard identity, relationship, or behavior is added, node names or application `extras` can provide equivalent nonportable discovery.
- **LOOK-13 — Contributor metadata is unfinished (RC gate).** The README still contains “Additional contributors TBD.”

## JSON Schema and validation issues

- **SCH-01 — Semantic validation is not implemented (Blocker).** Index bounds, name equality, channel target type, character containment, skin membership, same-scene relationships, uniqueness, and animation-domain rules require validator logic beyond the provided schemas.
- **SCH-03 — Expression entries do not inherit `glTFProperty` (Major).** They manually declare `extensions` and `extras`, then forbid additional properties. Use a named child schema with `allOf: glTFProperty`.
- **SCH-04 — Extension-on-extension placement needs tooling support (Major).** The `KHR_character_expression.*` schema filenames introduce nested extension locations not used elsewhere in the current Khronos set. Document and test how validators discover these schemas.
- **SCH-05 — Required arrays are structurally nonempty but semantically unchecked (Major).** Channel arrays can reference the wrong animation domain; mask arrays can contain self/duplicate/unknown entries.
- **SCH-06 — Mapping dictionaries may be empty (Major).** `expressionSetMappings`, individual expression sets, `skeletalRigMappings`, and individual rig maps need `minProperties` if empty objects are useless.
- **SCH-07 — Dictionary keys have no constraints (Major).** Add `propertyNames` rules for nonempty identifiers, namespace syntax, and any reserved names.
- **SCH-08 — Standard-value `anyOf` schemas are redundant (Minor).** `poseType` accepts every string, and mask `type` accepts every nonempty string, so standard `const` branches do not constrain data.
- **SCH-09 — Conditional property rules are absent (Major).** Mask properties and camera-hint properties validate in combinations for which the specification defines no behavior.
- **SCH-10 — Duplicate semantic references are not caught (Major).** JSON Schema `uniqueItems` only catches identical JSON values, not repeated `source` indices, node mappings, or masks with the same semantic endpoints.
- **SCH-11 — Defaults are not consistently safe (Major).** An empty reference-pose object defaults to T-pose; an omitted mask type defaults to blend. Defaults must be valid without hidden semantic prerequisites.
- **SCH-14 — No version/future-extension strategy exists for dictionary objects (Major).** Mapping dictionaries themselves are not `glTFProperty` objects, so a mapping set cannot carry `extensions` or `extras` without colliding with ordinary mapping keys.

## Naming and terminology issues

- **NAME-01 — `morphtarget` should be reviewed as `morph_target` (Major).** This is the last safe time to fix the public extension name.
- **NAME-02 — `lookat` should be reviewed as `look_at` (Minor).** Use consistent English tokenization across extension names and prose.
- **NAME-03 — `expression` is both object type and label property (Minor).** `expressions[].name`, `id`, or `semantic` would be clearer than `expressions[].expression`.
- **NAME-04 — `joint` may be false terminology (Major).** Unless targets are validated as skin joints, use `node_transform`.
- **NAME-05 — `texture` is broader than texture transform (Major).** Rename or expand it before RC.
- **NAME-06 — `third_person` means “not first person” (Major).** The token name and truth table disagree.
- **NAME-07 — `hint` versus normative behavior is inconsistent (Major).** If a supporting runtime must honor standard roles, the feature is a view-context annotation; if it may ignore them, `extensionsRequired` is inappropriate.
- **NAME-08 — `label` versus `name` is inconsistent (Minor).** Define a project-wide rule for human-readable labels, debugging names, stable identifiers, and localization.
- **NAME-09 — Mapping endpoint terminology is inconsistent (Major).** `KHR_character_skeleton_mapping` uses `node` for the model-side endpoint, while `KHR_character_expression_mapping` uses `source` for the analogous endpoint. Expression mapping, masking, constraints, and skeleton mapping also use `source` and `target` differently. Define a common terminology and data-flow direction, or explain why the terms intentionally differ.
- **NAME-10 — Pose type spelling is inconsistent with other tokens (Minor).** Decide between `TPose`/`APose`/`IPose` and a consistent style such as `t_pose`/`a_pose`/`i_pose`, including custom-name collision rules.
- **NAME-11 — Rig and expression-set container names are overly abstract (Minor).** `skeletalRigMappings` and `expressionSetMappings` do not reveal identity/version requirements. Settle the identity model before shortening or freezing property names.

## Documentation and examples issues

- **DOC-12 — Private or unstable working documents remain referenced (Major).** Replace the Google “Expressions Tab” reference with public specification text.
- **DOC-13 — Examples repeat grammar and factual errors (Minor).** Examples include a skeleton whose mapped limbs are outside the root hierarchy and a morph-target fragment that claims an index it does not contain. Audit every explanatory sentence against its JSON.
- **DOC-16 — No performance guidance is measured (Minor).** Primitive suppression, repeated animation evaluation, material cloning, and many mapping sets may be expensive. Provide representative measurements without making them normative.
- **DOC-17 — Scope exclusions need normative consequences (Major).** “Known limitations” that cause divergent output—especially animation mixing and target selection—must be resolved or turned into explicit validity restrictions before RC.

## Proposed resolution order

1. Define the object/ownership model: one character per asset, scene membership, and skin association.
2. Define the expression execution model with exact sampling and mixing equations, then decide whether separate channel-type extensions remain necessary.
3. Resolve the node-visibility inheritance contradiction and define a per-view render predicate shared by node and primitive visibility.
4. Simplify camera and look-at metadata into testable roles and explicit relationships; remove examples whose behavior is not encoded.
5. Freeze extension/property/token names.

## Minimum RC acceptance checklist

- [ ] Every standard token has a normative, testable behavior.
- [ ] Expression value-to-animation sampling is exact.
- [ ] Overlapping expression outputs are deterministic or prohibited.
- [ ] Scene membership and skins have defined scope.
- [ ] Visibility inheritance and `KHR_node_visibility` composition are consistent.
- [ ] Camera target orientation and role-specific property combinations are complete.
- [ ] Reference poses select a skin/rig and obey static-pose constraints.
- [ ] Skeleton and expression mappings have deterministic semantics.
- [ ] No normative requirement exists only in a PR comment or private document.
